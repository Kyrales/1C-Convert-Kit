# План стабилизации и ускорения GUI (src/gui) от модели GPT-5.2

## Контекст

GUI реализован на FreeSimpleGUI/PySimpleGUI и состоит из следующих ключевых модулей:

- `src/gui/main.py` — точка входа, создаёт окно и запускает цикл событий.
- `src/gui/main_window.py` — основной класс `CyberpunkGUI`: layout, события, состояние, файловые операции, чтение `.env`.
- `src/gui/project_scanner.py` — сканирование проектов в `projects/`.
- `src/gui/project_editor.py` — диалоги Add/Edit/Copy и сбор параметров `.env`.
- `src/gui/conversion_runner.py` — запуск `src/core/convert.py` в фоне (thread) и прокидывание прогресса/логов в окно событиями.

## Критичные замечания (стабильность и скорость)

### 1) Переполнение очереди событий из-за логов (event flood)

Текущее поведение:

- `conversion_runner.py` отправляет событие в окно на каждую строку stdout процесса.
- `main_window.py` на каждое событие делает обновление `Multiline`.

Риски:

- заметные лаги UI и “подвисания” на большом объёме вывода;
- рост потребления памяти из-за неограниченного накопления текста;
- ухудшение отзывчивости по мере роста лога.

### 2) Неполное управление жизненным циклом конвертации

Текущее поведение:

- отсутствует жёсткая гарантия “одна конвертация за раз” (можно повторно нажать “Выполнить”);
- остановка реализована флагом `is_running`, без надёжного завершения дочернего процесса на Windows;
- при закрытии окна фоновая конвертация останавливается “мягко”, без ожидания завершения потока.

Риски:

- “осиротевшие” процессы `python`, которые продолжают работать после закрытия GUI;
- исключения и нестабильность при попытке писать события в закрытое окно;
- гонки состояний при повторных запусках.

### 3) Обращение к элементам GUI из фонового потока

Текущее поведение:

- фоновый поток читает значение чекбокса `-DEBUG-` напрямую через `window[...]`.

Риски:

- Tk и обёртки SimpleGUI не гарантируют потокобезопасность: редкие, но тяжёлые фризы/краши.

### 4) Лишний I/O при обновлении таблицы проектов

Текущее поведение:

- `update_table()` всегда вызывает `update_details_table()`;
- `update_details_table()` каждый раз перечитывает базовый `.env` и `.env` проекта.

Риски:

- деградация отзывчивости UI (особенно на сетевых путях, при антивирусе, при большом числе проектов).

### 5) Недетерминированный выбор `.env` файлов

Текущее поведение:

- “базовый `.env`” выбирается как “первый найденный” в `projects/`;
- “проектный `.env`” выбирается как “первый найденный” `*.env` в папке проекта.

Риски:

- разные конфигурации на разных ПК/после копирования папок;
- трудно воспроизводимые ошибки.

### 6) Производительность конвертации ограничена запуском subprocess на каждый проект

Текущее поведение:

- на каждый проект поднимается новый процесс `python convert.py ...`.

Риски:

- высокая стоимость старта интерпретатора + импортов;
- дополнительная сложность с кодировками/буферизацией/ANSI.

## План переделки (этапы с деталями)

### Этап 1 — Стабилизация event loop и логов (максимальный эффект для UI)

Цель: убрать фризы и обеспечить предсказуемую работу на длинных запусках.

Что сделать:

1. Добавить буферизацию логов в `ConversionRunner`:
   - накапливать строки в буфере;
   - отправлять в GUI пачками (по таймеру или при достижении размера).
2. Ограничить размер текста лога в GUI:
   - хранить только последние N строк или последние X МБ;
   - при превышении — обрезать начало текста.
3. Убрать любые обращения к `window[...]` из фонового потока:
   - передавать `debug_mode` как snapshot-параметр при старте конвертации;
   - в фоне использовать только `write_event_value`.

Критерии приёмки:

- UI остаётся отзывчивым на длительной конвертации и большом выводе.
- Память процесса GUI не растёт неограниченно из-за лога.

### Этап 2 — Надёжный жизненный цикл конвертации и остановка

Цель: исключить “осиротевшие” процессы и гонки.

Что сделать:

1. Ввести явное состояние выполнения:
   - `IDLE/RUNNING/CANCELING` (или аналогичное);
   - запрет повторного запуска, пока `RUNNING`.
2. Управление дочерним процессом:
   - хранить ссылку на `subprocess.Popen` для текущего проекта;
   - при отмене: `terminate()` → `wait(timeout)` → `kill()` → `wait()`.
3. Сделать `stop()` реально прерывающим выполнение:
   - `stop()` должен не только выставлять флаг, но и завершать текущий `Popen`, чтобы разблокировать чтение stdout (`readline()`).
4. Корректное завершение при закрытии окна:
   - инициировать stop;
   - дождаться завершения фонового потока (join с таймаутом);
   - только после этого закрывать окно.

Критерии приёмки:

- после закрытия окна не остаётся активных процессов конвертации.
- повторное нажатие “Выполнить” во время работы не создаёт параллельные запуски.

### Этап 3 — Ускорение UI: кэширование `.env` и снижение I/O

Цель: сделать клики и обновления таблиц “лёгкими”.

Что сделать:

1. Кэшировать загруженные параметры:
   - базовый `.env` читать один раз и хранить;
   - параметры выбранного проекта читать только при смене выделения или после операций редактирования.
2. Развязать `update_table()` и обновление деталей:
   - не перечитывать `.env` при любом обновлении таблицы (например, при переключении чекбокса).
3. Сохранять состояние GUI вне исходников (опционально, но полезно для UX):
   - сохранять размеры окна, последний путь, debug по умолчанию;
   - хранить конфиг в профиле пользователя (Windows: `%APPDATA%`/`%LOCALAPPDATA%`) или отдельном “data/config” рядом с `projects/`.

Критерии приёмки:

- переключение строк/чекбоксов не вызывает заметных задержек.

### Этап 4 — Детерминированные правила выбора `.env`

Цель: воспроизводимость конфигураций.

Что сделать:

1. Зафиксировать правило выбора базового `.env`:
   - рекомендуемый вариант: файл с фиксированным именем (например, `projects/base.env` или `projects/base_1.env`);
   - альтернативно: сортировка и выбор “первого по имени”.
2. Зафиксировать правило выбора `.env` проекта:
   - сортировка `*.env` по имени и явный выбор;
   - либо хранение конкретного файла в проекте по шаблону.

Критерии приёмки:

- одинаковая папка `projects/` даёт одинаковые результаты на разных машинах.

### Этап 5 — Разделение ответственности (архитектура для дальнейшего развития)

Цель: повысить тестируемость и снизить риск регрессий.

Что сделать:

1. Выделить слой работы с проектами (CRUD + файловые операции).
2. Выделить слой работы с env (поиск/мердж/кэш/правила выбора).
3. Выделить слой выполнения конвертации (прогресс, отмена, лог-буфер).
4. `CyberpunkGUI` оставить тонким: отображение + маршрутизация событий.
5. Типизировать контракт событий и отвязать runner от `window`:
   - структурировать payload событий (`-LOG-`, `-UPDATE_STATUS-`, `-CONVERSION_DONE-`);
   - ввести минимальный интерфейс “доставки событий” (event sink) вместо прямой зависимости от объекта окна.

Критерии приёмки:

- основные сценарии (scan/add/edit/copy/delete/run/cancel) проверяются изолированно без GUI.

### Этап 6 (опционально) — Ускорение конвертации без subprocess на проект

Цель: уменьшить накладные расходы и упростить логирование.

Что сделать:

1. Убрать “subprocess на проект” через промежуточные варианты:
   - один subprocess на батч проектов (один запуск Python на всю пачку);
   - либо долгоживущий worker-процесс с IPC (очередь/pipe), который принимает команды и отдает прогресс/логи.
2. Вынести API-уровень в `src/core/convert.py` (или рядом), который принимает список env-файлов/путь проекта и возвращает результат.
3. Рассмотреть вызов конвертации в процессе GUI только если критично ускорение и приемлемы риски:
   - обеспечить изоляцию ошибок (например, защитные границы на уровне задач, аккуратная обработка исключений);
   - логи направлять в GUI через callback/очередь, сохранив поддержку “тихого” режима.

Критерии приёмки:

- суммарное время пакетной конвертации снижается за счёт отсутствия стартов процессов.

### Дополнения и уточнения (Review & Refinements по текущей реализации)

Проведен анализ текущего кода (`src/gui/conversion_runner.py`, `src/gui/main_window.py`) и выявлены следующие практические нюансы, которые важно отразить в плане:

1.  **Блокирующий I/O при чтении stdout и “мягкая” остановка**:
    *   В текущем коде используется `process.stdout.readline`, что является блокирующей операцией. Если дочерний процесс перестанет печатать вывод (или зависнет), поток конвертации может повиснуть на чтении. Проверка флага остановки выполняется только после прочтения строки, поэтому `stop()` в виде “только флаг” не гарантирует быструю отмену.
    *   **Уточнение решения**: хранить ссылку на `subprocess.Popen` текущего проекта (например, `self.current_process`) и в `stop()` пытаться завершить процесс напрямую. Для надежности на Windows: `terminate()` → `wait(timeout)` → `kill()` → `wait()` (это логически относится к Этапу 2, но нужно как часть механики stop/cancel).

2.  **Семантика “decoupling” для этого GUI**:
    *   Сейчас `ConversionRunner` принимает `window` и вызывает `write_event_value` напрямую. Это связывает runner с GUI и затрудняет тестирование.
    *   **Уточнение решения**: ввести минимальный интерфейс “доставки событий” (event sink) вместо прямой зависимости от `window`. Технически это может быть и callbacks, и объект с методами `emit_log/emit_status/emit_progress`, который внутри уже делает `write_event_value`.

3.  **Сохранение состояния GUI: где хранить конфиг**:
    *   Идея сохранять настройки GUI (размер окна, последние пути, debug по умолчанию) полезна, но путь `src/gui/config.json` нежелателен как место для изменяемых пользовательских данных.
    *   **Уточнение решения**: хранить конфиг в пользовательском профиле (Windows: `%APPDATA%`/`%LOCALAPPDATA%`) или в отдельном “data/config” каталоге рядом с `projects/` как opt-in.

4.  **Типизация как практический инструмент стабилизации**:
    *   В коде много `type: ignore`. Это снижает ценность type-checking и усложняет рефакторинг.
    *   **Уточнение решения**: при Этапе 5 ввести типы для событий/сообщений (`TypedDict` для payload `-LOG-`, структурированный тип прогресса) и Protocol для интерфейса доставки событий.

5.  **Ускорение без “import convert.py”: промежуточный вариант**:
    *   Прямой вызов конвертации внутри процесса GUI (через import) действительно быстрее, но снижает изоляцию: ошибки/утечки в конвертере напрямую ухудшают стабильность GUI.
    *   **Уточнение решения**: перед переходом к “всё внутри процесса GUI” рассмотреть вариант “один subprocess на батч” или “долгоживущий worker-процесс” с IPC. Это убирает оверхед старта Python “на проект”, сохраняя изоляцию.
