# Спецификация: Группировка проектов по папкам в главном окне

## 1. Обзор

### 1.1 Цель
Добавить в GUI поддержку групп проектов на основе вложенных папок в каталоге `projects/`, чтобы пользователь мог удобнее организовывать конвертеры по предметным областям, продуктам или командам, например `Demo`, `БП` и другим.

### 1.2 Контекст
Сейчас главное окно GUI показывает проекты плоским списком. При этом в файловой системе уже могут существовать подпапки внутри `projects/`, например `projects/Demo/`, где лежат несколько проектов. Текущий интерфейс и `ProjectScanner` ориентированы только на верхний уровень и не позволяют:

- видеть группы как отдельные элементы списка
- заходить внутрь группы
- запускать обработку всей группы целиком
- перемещать проекты и группы между группами
- создавать группы из интерфейса

### 1.3 Ожидаемый результат
GUI должен поддерживать навигацию по иерархии папок проектов с ограничением глубины вложенности до 4 уровней, сохраняя существующую модель работы с проектами `.env`, правила фильтрации служебных папок и пакетный запуск конвертаций.

## 2. Требования

### 2.1 Функциональные требования

#### FR-1: Отображение групп проектов
**Приоритет:** Высокий  
**Описание:** Главное окно должно отображать не только проекты, но и группы, соответствующие папкам внутри `projects/`.

**Критерии приемки:**
- 1.1. Любая папка внутри `projects/`, содержащая проекты или вложенные группы, отображается в интерфейсе как группа
- 1.2. Группа `projects/Demo/` отображается в списке как элемент `Demo`
- 1.3. Проектом считается папка, в которой найден хотя бы один `.env` файл проекта с валидным `ScriptName`
- 1.4. Группой считается папка, в которой нет собственного `.env` проекта с валидным `ScriptName`, но есть вложенные корректные проекты или вложенные группы
- 1.5. В одном списке допускается совместное отображение проектов и групп текущего уровня, при этом все группы должны отображаться вверху списка
- 1.6. Для групп в интерфейсе используется визуально отличимый красивый значок группы
- 1.7. Базовый `.env` в корне `projects/` продолжает работать как общий файл настроек и не отображается как проект или группа
- 1.8. Служебные и мусорные папки не отображаются как группы или проекты
- 1.9. Правила фильтрации служебных папок должны как минимум исключать каталоги, начинающиеся с `.`, `__` и `~`
- 1.10. Папка с `.env`, но без валидного `ScriptName`, не считается проектом и не должна автоматически отображаться как группа только из-за наличия `.env`

#### FR-2: Навигация по группам
**Приоритет:** Высокий  
**Описание:** Пользователь должен иметь возможность заходить в группу и возвращаться обратно по уровням вложенности.

**Критерии приемки:**
- 2.1. Двойной щелчок левой кнопкой мыши по наименованию группы открывает ее содержимое
- 2.2. После открытия группы в таблице отображаются только проекты и подгруппы выбранной группы
- 2.3. Пользователь может вернуться на уровень выше через отдельную кнопку `..` в интерфейсе, аналогично файловым менеджерам
- 2.4. В интерфейсе отображается текущий контекст навигации, например путь группы или хлебные крошки
- 2.5. При переходе между уровнями выделение элементов сбрасывается
- 2.6. Открытие обычного проекта двойным щелчком не должно ошибочно открывать навигацию по группам

#### FR-3: Создание группы из GUI
**Приоритет:** Высокий  
**Описание:** Пользователь должен создавать новую группу через главное окно без ручного создания папки в файловой системе.

**Критерии приемки:**
- 3.1. В интерфейсе доступна кнопка `Добавить группу`
- 3.2. При нажатии открывается ввод имени группы
- 3.3. После подтверждения создается папка внутри текущего уровня каталога `projects/`
- 3.4. Если пользователь находится внутри группы, новая группа создается внутри текущей группы
- 3.5. Имя группы валидируется на недопустимые символы имени папки Windows
- 3.6. Нельзя создать группу с именем, уже занятым проектом или группой на этом же уровне
- 3.7. После успешного создания список обновляется без необходимости перезапуска GUI
- 3.8. В лог выводится понятное сообщение об успешном создании группы
- 3.9. Имя группы может содержать латиницу, кириллицу, цифры, символы `_`, `-` и пробелы, при этом имя должно начинаться с буквы или цифры
- 3.10. Имя группы не должно начинаться с служебных префиксов `.`, `__` или `~`
- 3.11. Создание групп через файловую систему допускается, GUI должен корректно подхватывать такие группы при обновлении списка

#### FR-4: Выполнение группы целиком
**Приоритет:** Высокий  
**Описание:** Пользователь должен иметь возможность выделить группу и выполнить последовательно все проекты внутри нее.

**Критерии приемки:**
- 4.1. Одинарный левый клик позволяет выделить группу для выполнения
- 4.2. При нажатии `ВЫПОЛНИТЬ` для выделенной группы запускаются все проекты, найденные внутри группы и всех допустимых вложенных подгрупп
- 4.3. Выполнение происходит последовательно в предсказуемом порядке
- 4.4. Порядок выполнения соответствует depth-first обходу дерева: элементы текущего уровня обрабатываются сверху вниз, и каждая группа полностью раскрывается перед переходом к следующей соседней группе
- 4.5. Если одновременно выделены проект и группа, в итоговый список попадают все уникальные проекты без дублирования
- 4.6. Если группа после фильтрации не содержит ни одного проекта, выполнение не приводит к аварии и дает понятное предупреждение пользователю
- 4.7. Прогресс и лог выполнения продолжают показывать текущий обрабатываемый проект, а не только имя группы
- 4.8. Если после раскрытия всех выделенных элементов итоговый список проектов пуст, GUI показывает предупреждение и не запускает `ConversionRunner`

#### FR-5: Перемещение проектов и групп
**Приоритет:** Высокий  
**Описание:** Пользователь должен иметь возможность перемещать проекты и группы между группами и в корень каталога `projects/`.

**Критерии приемки:**
- 5.1. В интерфейсе доступна кнопка `Переместить в группу`
- 5.2. Команда доступна для одного или нескольких выделенных проектов и групп
- 5.3. В диалоге выбора назначения можно выбрать существующую группу или корень `projects/`
- 5.4. После подтверждения выполняется физическое перемещение папок в файловой системе
- 5.5. После перемещения список проектов и групп обновляется автоматически
- 5.6. Перемещение группы внутрь самой себя или любой своей подгруппы запрещено
- 5.7. При конфликте имен в папке назначения операция не выполняется, а пользователь получает понятное сообщение
- 5.8. При перемещении проекта его `.env` файл и прочее содержимое сохраняются без изменений
- 5.9. При перемещении группы вместе с ней перемещается все вложенное содержимое
- 5.10. При перемещении проекта или группы содержимое `.env` файлов не переписывается автоматически
- 5.11. Если внутри `.env` используются относительные пути, пользователь несет ответственность за их корректность после перемещения
- 5.12. Перед подтверждением перемещения GUI предупреждает пользователя, что относительные пути в `.env` после перемещения не пересчитываются автоматически

#### FR-6: Ограничение глубины вложенности
**Приоритет:** Высокий  
**Описание:** Иерархия групп должна быть ограничена максимум четырьмя уровнями вложенности относительно каталога `projects/`.

**Критерии приемки:**
- 6.1. Максимально допустимая глубина группы составляет 4 уровня
- 6.2. Сканирование не должно приводить к ошибке при наличии более глубокой структуры на диске
- 6.3. Если пользователь пытается создать группу глубже 4 уровня, GUI блокирует операцию с понятным сообщением
- 6.4. Если пользователь пытается переместить проект или группу так, что итоговая глубина превысит 4 уровня, операция запрещается
- 6.5. При обнаружении структуры глубже 4 уровней, созданной вне GUI, такие элементы не должны приводить к падению интерфейса
- 6.6. Для элементов глубже лимита используется единое поведение: они не отображаются в списке и фиксируются предупреждением в лог при обновлении дерева

#### FR-7: Совместимость с текущими операциями над проектами
**Приоритет:** Высокий  
**Описание:** Добавление групп не должно ломать уже существующие сценарии создания, редактирования, копирования, удаления и запуска отдельных проектов.

**Критерии приемки:**
- 7.1. Создание проекта из GUI сохраняет текущую модель: проект создается как папка с `.env` файлом
- 7.2. Если пользователь находится внутри группы, новый проект создается внутри текущей группы
- 7.3. Редактирование проекта продолжает работать для проектов внутри групп
- 7.4. Копирование проекта продолжает работать для проектов внутри групп
- 7.5. Удаление проекта продолжает работать для проектов внутри групп
- 7.6. Удаление группы возможно только с явным подтверждением пользователя
- 7.7. Удаление непустой группы сопровождается отдельным предупреждением о вложенных проектах и подгруппах

#### FR-8: Актуализация сканирования и модели данных
**Приоритет:** Высокий  
**Описание:** Поддержка групп должна быть реализована на уровне сканирования каталога `projects/` и внутренней модели элементов GUI.

**Критерии приемки:**
- 8.1. `ProjectScanner` должен уметь рекурсивно обходить структуру проектов и групп
- 8.2. Сканер должен различать тип элемента: `project` или `group`
- 8.3. Для каждого элемента должны быть доступны данные, достаточные для навигации, отображения и перемещения
- 8.4. Для проекта должен сохраняться путь к `.env`, `ScriptName`, путь выгрузки и прочие текущие атрибуты
- 8.5. Для группы должен сохраняться путь папки, уровень вложенности и информация о наличии дочерних элементов
- 8.6. Обновление списка в GUI должно происходить на основе текущего уровня иерархии, а не только полного плоского списка
- 8.7. Сканер должен применять те же правила фильтрации служебных папок, что и текущий GUI
- 8.8. Сканер не должен считать папку проектом, если `.env` не содержит валидный `ScriptName`

#### FR-9: Пользовательский пример
**Приоритет:** Средний  
**Описание:** Функционал должен корректно работать на реальном сценарии с папкой `projects/Demo/`.

**Критерии приемки:**
- 9.1. Если на диске существует папка `f:\\1C\\Projects\\1c-convert-kit\\projects\\Demo\\`
- 9.2. И внутри нее находятся три корректных проекта
- 9.3. То на верхнем уровне GUI отображается группа `Demo`
- 9.4. По двойному щелчку по `Demo` пользователь видит три проекта внутри
- 9.5. При выделении `Demo` и запуске `ВЫПОЛНИТЬ` выполняются все три проекта по порядку

### 2.2 Нефункциональные требования

#### NFR-1: Производительность
- Обновление списка проектов и групп должно оставаться визуально быстрым для типичных рабочих структур
- Рекурсивное сканирование не должно заметно ухудшить старт GUI по сравнению с текущим сценарием для малых и средних наборов проектов

#### NFR-2: Совместимость
- Решение должно работать в текущем Windows-окружении проекта
- Структура проектов на диске должна оставаться совместимой с существующей логикой `load_env_file()` и `merge_env_files()`
- Базовые `.env` файлы в корне `projects/` не должны терять свое текущее поведение

#### NFR-3: Удобство использования
- Навигация по группам должна быть понятной без чтения документации
- Пользователь должен различать проект и группу визуально с первого взгляда
- Для группы должен использоваться красивый и понятный значок, заметно отличающийся от проекта
- Основные действия с группами должны быть доступны из главного окна без ручной работы с проводником

#### NFR-4: Надежность
- Ошибки файловых операций должны обрабатываться без падения GUI
- Любая ошибка создания, удаления или перемещения должна сопровождаться понятным сообщением на русском языке
- Частично выполненные операции перемещения должны быть исключены или корректно откатываться

#### NFR-5: Поддерживаемость
- Новая логика группировки должна быть выделена в переиспользуемые части, без дублирования между GUI-обработчиками
- Типы данных для элементов списка должны явно отражать различие между проектом и группой
- Новые правила глубины и перемещения должны быть покрыты тестами

## 3. Архитектура

### 3.1 Изменяемые области

- `src/gui/main_window.py` - отображение групп, навигация, новые кнопки, обработка двойного щелчка и перемещения
- `src/gui/project_scanner.py` - рекурсивное сканирование дерева проектов и групп
- `src/gui/project_editor.py` - при необходимости поддержка создания проекта в текущей группе
- `src/gui/conversion_runner.py` - прием итогового плоского списка проектов для запуска группы
- `tests/unit/` - тесты сканера, навигации и правил перемещения
- `tests/integration/` - сценарии запуска группы и работы GUI-логики

### 3.2 Логическая модель

Предлагается ввести две сущности:

- `ProjectItem` - проект, соответствующий папке с `.env` файлом
- `GroupItem` - группа, соответствующая папке без собственного `.env`, но содержащей вложенные элементы

Общие свойства элемента списка:

- отображаемое имя
- абсолютный путь
- тип элемента
- уровень вложенности

Дополнительные свойства проекта:

- путь к `.env`
- `ScriptName`
- `V8_DST_PATH`
- временно измененный путь выгрузки

Дополнительные свойства группы:

- список дочерних элементов или возможность быстро их получить
- количество вложенных проектов

### 3.3 Поток работы пользователя

```
1. GUI сканирует каталог projects рекурсивно
2. На верхнем уровне отображаются проекты и группы
3. Пользователь двойным щелчком открывает нужную группу
4. Пользователь выделяет проект, несколько проектов, группу или несколько групп
5. GUI преобразует выделение в итоговый список уникальных проектов
6. ConversionRunner запускает проекты последовательно
7. Пользователь может создать новую группу или переместить элементы между группами
```

## 4. Правила предметной области

### 4.1 Определение проекта и группы
- Папка с `.env` файлом и валидным `ScriptName` считается проектом
- Папка без собственного валидного проекта, содержащая вложенные корректные проекты или группы, считается группой
- Пустые папки не отображаются как группы по умолчанию
- Служебные папки, начинающиеся с `.`, `__` или `~`, не отображаются в дереве
- Корень `projects/` является контейнером и не считается группой в пользовательском списке

### 4.2 Правила глубины
- Уровень `projects/<group>` считается глубиной 1
- Уровень `projects/<group>/<group>` считается глубиной 2
- Максимум допускается глубина 4

### 4.3 Правила порядка выполнения
- По умолчанию используется стабильный предсказуемый порядок обхода
- Используется depth-first порядок обхода: элементы текущего уровня сортируются по правилам интерфейса, затем каждая группа полностью раскрывается рекурсивно до перехода к следующему соседнему элементу
- Порядок должен быть одинаковым при отображении в GUI и при пакетном выполнении группы

## 5. Тестирование

### 5.1 Unit-тесты
- Сканирование корня `projects/` с группами и проектами
- Определение типа элемента: проект или группа
- Ограничение глубины вложенности
- Запрет перемещения группы в саму себя или в подгруппу
- Формирование итогового списка проектов при выборе группы
- Отсутствие дублирования проектов при смешанном выборе

### 5.2 Интеграционные тесты
- Отображение группы `Demo` на верхнем уровне
- Вход в группу `Demo` и отображение вложенных проектов
- Выполнение всей группы `Demo`
- Создание новой группы из GUI
- Перемещение проекта в группу и обратно в корень

### 5.3 Тестовые данные
- Использовать существующие фикстуры `tests/fixtures/` как базу для проектов
- Добавить тестовую структуру с вложенными группами глубиной от 1 до 4
- Добавить отдельную фикстуру со структурой глубже 4 уровней для проверки ограничений

## 6. Риски и ограничения

### 6.1 Риски
- **Риск:** Неоднозначность между папкой-проектом и папкой-группой
  - **Митигация:** Зафиксировать единое правило на основе наличия `.env` файла с валидным `ScriptName` и фильтрации служебных папок

- **Риск:** Регрессии в существующих действиях GUI над проектами
  - **Митигация:** Покрыть тестами сценарии add/edit/copy/delete для проектов внутри групп

- **Риск:** Ошибки при перемещении папок в файловой системе
  - **Митигация:** Централизовать проверки перед перемещением и обрабатывать конфликты имен

- **Риск:** Потеря понятности интерфейса при добавлении иерархии
  - **Митигация:** Показать текущий путь, отличать группы визуально и добавить явный переход на уровень выше

### 6.2 Ограничения
- Максимальная вложенность групп не более 4
- Поддержка ориентирована на Windows-файловую систему
- Группы являются отражением реальных папок на диске, а не отдельной логической сущностью вне файловой структуры

## 7. Критерии успеха

1. Пользователь видит существующие папки внутри `projects/` как группы в GUI
2. Пользователь может открыть группу двойным щелчком и увидеть вложенные проекты
3. Пользователь может запустить выполнение всей группы одной командой
4. Пользователь может создать группу и переместить проекты или группы через GUI
5. Ограничение глубины 4 уровня соблюдается при создании и перемещении
6. Существующие сценарии работы с одиночными проектами не сломаны
