# Дизайн: Группировка проектов по папкам в главном окне

## 1. Обзор архитектуры

### 1.1 Принципы дизайна
- **Совместимость с текущим GUI**: новая функциональность встраивается в существующие `CyberpunkGUI`, `ProjectScanner` и `ConversionRunner`, без смены базовой модели проекта как папки с `.env`
- **Файловая система как источник истины**: группы отражают реальные папки внутри `projects/`
- **Явное разделение типов**: проект и группа имеют разные типы элементов и разное поведение в интерфейсе
- **Предсказуемая навигация**: поведение должно быть похоже на файловый менеджер, включая кнопку `..`
- **Безопасность файловых операций**: создание, удаление и перемещение выполняются только после валидации пути, глубины и конфликтов имен
- **Разделение модели и состояния UI**: дерево элементов хранится отдельно от текущего выделения в интерфейсе

### 1.2 Архитектурные слои

```
┌──────────────────────────────────────────────────────┐
│                GUI Presentation Layer               │
│     (main_window.py: таблица, кнопки, навигация)    │
└──────────────────────────────────────────────────────┘
                          ↓
┌──────────────────────────────────────────────────────┐
│                 GUI State Layer                     │
│   (текущая группа, breadcrumbs, выделение, фильтр)  │
└──────────────────────────────────────────────────────┘
                          ↓
┌──────────────────────────────────────────────────────┐
│               Project Tree Service Layer            │
│ (project_scanner.py: дерево групп/проектов, обход)  │
└──────────────────────────────────────────────────────┘
                          ↓
┌──────────────────────────────────────────────────────┐
│              File System Operation Layer            │
│    (create group, move, delete, depth validation)   │
└──────────────────────────────────────────────────────┘
                          ↓
┌──────────────────────────────────────────────────────┐
│                 Existing Conversion Layer           │
│      (conversion_runner.py, convert.py, .env)       │
└──────────────────────────────────────────────────────┘
```

## 2. Изменяемые модули

### 2.1 `src/gui/project_scanner.py`
Отвечает за рекурсивное сканирование `projects/`, построение дерева элементов, фильтрацию по текущему уровню и разворачивание группы в плоский список проектов для запуска.

### 2.2 `src/gui/main_window.py`
Отвечает за:

- отображение групп и проектов в одном списке
- сортировку групп выше проектов
- красивый значок группы
- навигацию двойным щелчком по наименованию
- кнопку `..` для перехода вверх
- кнопку `Добавить группу`
- кнопку `Переместить в группу`
- сброс выделения при смене уровня
- запуск выбранных групп и проектов

### 2.3 `src/gui/conversion_runner.py`
Сохраняет текущую ответственность, но получает уже нормализованный плоский список проектов без групп и без дублей.

### 2.4 `tests/unit/` и `tests/integration/`
Покрывают дерево проектов, правила глубины, перемещение, навигацию и формирование списка проектов для выполнения.

## 3. Модель данных

### 3.1 Общая идея
Текущий `ProjectDict` недостаточен, потому что он описывает только проект верхнего уровня. Для новой функциональности нужна единая модель элементов дерева.

### 3.2 Предлагаемые типы

```python
class BaseTreeItem(TypedDict):
    item_type: str              # "project" | "group"
    name: str
    path: str
    relative_path: str
    depth: int


class ProjectTreeItem(BaseTreeItem):
    item_type: Literal["project"]
    env_path: str
    script: str
    dst_path: str
    custom_dst_path: str | None


class GroupTreeItem(BaseTreeItem):
    item_type: Literal["group"]
    child_count: int
    project_count: int
    children: list[str]         # список relative_path дочерних элементов
```

### 3.3 Причины такой модели
- `item_type` устраняет неоднозначность поведения в GUI
- `relative_path` упрощает breadcrumbs и проверку глубины
- `depth` нужен для ограничений вложенности
- `project_count` пригодится для диалога перемещения и запуска группы
- `children` позволяет хранить иерархию явно, без восстановления ее только по `relative_path`

### 3.4 Состояние UI
Выделение и текущая строка не входят в модель дерева. Их предлагается хранить отдельно:

```python
self.selected_paths: set[str]
self.selected_row: int | None
```

Это упрощает сброс выделения при смене уровня и не смешивает файловую модель со временным состоянием GUI.

## 4. Правила определения элементов

### 4.1 Проект
Папка считается проектом, если в ней найден хотя бы один `.env` файл проекта с валидным `ScriptName`.

### 4.2 Группа
Папка считается группой, если:

- в ней нет собственного `.env` файла проекта с валидным `ScriptName`
- и она содержит вложенные корректные проекты или группы

Пустые папки не отображаются как группы по умолчанию, чтобы не показывать случайные или служебные каталоги.

### 4.3 Корень
Каталог `projects/` является контейнером верхнего уровня и не отображается как отдельная группа.

### 4.4 Базовый `.env`
`.env` в корне `projects/` продолжает использоваться как базовый файл конфигурации и игнорируется при построении списка элементов.

### 4.5 Служебные папки
Каталоги, начинающиеся с `.`, `__` или `~`, не отображаются в дереве и не участвуют в запуске, навигации и перемещении.

## 5. Навигация и состояние GUI

### 5.1 Состояние навигации
В `CyberpunkGUI` предлагается хранить:

```python
self.project_tree: dict[str, BaseTreeItem]
self.current_group_path: Path | None
self.current_items: list[BaseTreeItem]
self.selected_paths: set[str]
self.selected_row: int | None
```

Дополнительно:

- `self.current_group_path is None` означает корень `projects/`
- `self.current_items` содержит только элементы текущего уровня
- `self.project_tree` хранит дерево по ключу `relative_path`
- `self.selected_paths` хранит множество путей элементов, отмеченных для пакетных операций и запуска
- `self.selected_row` хранит текущую строку таблицы для навигации и панели деталей
- `self.selected_row` и `self.selected_paths` обновляются независимо: курсор не обязан совпадать с выбранными для запуска элементами

### 5.2 Поведение открытия группы
При двойном щелчке по наименованию группы:

1. Проверяется, что строка относится к `group`
2. `current_group_path` меняется на путь группы
3. `current_items` обновляется дочерними элементами
4. выделение всех элементов сбрасывается
5. `selected_row` сбрасывается
6. таблица и breadcrumbs перерисовываются

### 5.3 Переход вверх
Кнопка `..`:

1. доступна только не в корне
2. переводит пользователя на родительский уровень
3. сбрасывает выделение элементов
4. обновляет таблицу и путь навигации

### 5.4 Отображение списка
Для текущего уровня должны действовать правила:

- сначала группы
- затем проекты
- внутри каждой категории сортировка по имени
- для группы отображается красивый значок группы
- для проекта сохраняется текущий формат отображения таблицы

## 6. Сканирование дерева проектов

### 6.1 Подход
`ProjectScanner` должен рекурсивно обойти каталог `projects/` и построить полное дерево элементов до допустимой глубины.

### 6.2 Основные методы

```python
TreeIndex = dict[str, BaseTreeItem]

class ProjectScanner:
    @staticmethod
    def build_tree() -> TreeIndex:
        pass

    @staticmethod
    def list_level(parent_path: Path | None) -> list[BaseTreeItem]:
        pass

    @staticmethod
    def flatten_projects(items: list[BaseTreeItem]) -> list[ProjectTreeItem]:
        pass

    @staticmethod
    def validate_group_name(name: str) -> None:
        pass

    @staticmethod
    def validate_move_target(source_paths: list[Path], target_path: Path) -> None:
        pass

    @staticmethod
    def should_skip_dir(path: Path) -> bool:
        pass
```

### 6.3 Рекурсивный алгоритм

1. Начать с `PROJECTS_DIR`
2. Игнорировать файлы верхнего уровня, кроме базового `.env`
3. Для каждой подпапки:
4. Пропустить каталог, если он подходит под правило `should_skip_dir()`
5. Определить, является ли она проектом или группой
6. Если это группа, рекурсивно просканировать дочерние элементы
7. Если глубина больше 4, исключить элемент из отображаемого дерева и зафиксировать предупреждение
8. Вернуть стабильно отсортированный список

### 6.4 Обработка глубины
- `projects/Demo` имеет глубину 1
- `projects/Demo/BP` имеет глубину 2
- элементы глубже 4 уровней не должны ломать интерфейс
- GUI не должен позволять создать или переместить элемент на глубину больше 4
- элементы глубже 4 уровней скрываются из интерфейса и отмечаются предупреждением в лог

## 7. Создание группы

### 7.1 Поток создания

1. Пользователь нажимает `Добавить группу`
2. GUI показывает диалог ввода имени
3. Имя валидируется
4. Рассчитывается путь внутри текущей группы или корня
5. Проверяется отсутствие конфликта имен
6. Проверяется допустимая глубина
7. Создается папка
8. Список обновляется
9. В лог выводится сообщение об успехе

### 7.2 Валидация имени группы
Имя группы должно:

- содержать латиницу или кириллицу
- может содержать цифры, пробелы, `_` и `-`
- не содержать недопустимые символы Windows
- не начинаться с `.`, `__` или `~`
- не совпадать с существующим именем проекта или группы на текущем уровне

Рекомендуемое регулярное выражение:

```python
r"^(?!\.)(?!__)(?!~)[A-Za-zА-Яа-яЁё0-9][A-Za-zА-Яа-яЁё0-9 _-]*$"
```

## 8. Перемещение проектов и групп

### 8.1 Поток перемещения

1. Пользователь выделяет один или несколько элементов
2. Нажимает `Переместить в группу`
3. GUI показывает диалог выбора целевой группы или корня
4. Для каждой операции выполняется валидация
5. После подтверждения выполняется физическое перемещение через `shutil.move()`
6. Список обновляется
7. В лог выводится итог операции

### 8.1.1 Поведение `.env` при перемещении
- `.env` файлы перемещаются вместе с проектом или группой без изменения содержимого
- пути внутри `.env` автоматически не пересчитываются
- если пользователь использует относительные пути, их корректность после перемещения остается на ответственности пользователя
- перед подтверждением перемещения GUI показывает предупреждение об этом ограничении

### 8.2 Правила валидации перемещения
- нельзя переместить группу в саму себя
- нельзя переместить группу в одну из ее подгрупп
- нельзя превысить глубину 4
- нельзя допустить конфликт имени в целевой папке
- нельзя переместить элемент в тот же самый каталог без изменения структуры

### 8.3 Обработка ошибок
Если файловая операция завершилась ошибкой:

- GUI показывает понятное сообщение на русском языке
- список не должен остаться в частично несогласованном состоянии
- выполняется повторное сканирование дерева с диска

## 9. Выполнение групп

### 9.1 Преобразование выделения
Перед запуском GUI должен преобразовать пользовательское выделение в плоский список проектов:

- выделенный проект добавляется в результат
- выделенная группа раскрывается рекурсивно до списка проектов
- повторяющиеся проекты удаляются по абсолютному пути
- пустые группы не добавляют задач, но дают предупреждение

### 9.2 Порядок выполнения
Порядок должен быть стабильным и предсказуемым:

1. элементы текущего уровня сортируются так же, как в интерфейсе
2. каждая группа разворачивается depth-first: сначала все ее прямые элементы по правилам сортировки, затем вложенные группы рекурсивно
3. `ConversionRunner` получает итоговый список уже в правильной очередности

### 9.3 Прогресс и логирование
- в прогрессе отображается количество реально выполняемых проектов
- в логе отображается имя текущего проекта
- при выборе группы имя группы может выводиться только как контекстное сообщение, но не как единица выполнения

## 10. Изменения в интерфейсе

### 10.1 Новые элементы управления
- кнопка `Добавить группу`
- кнопка `Переместить в группу`
- кнопка `..`
- поле или текст с текущим путем группы

### 10.2 Изменения таблицы
Текущую таблицу можно сохранить, но дополнить:

- отображением значка группы в колонке имени
- сортировкой групп выше проектов
- возможностью надежно распознать двойной щелчок по имени группы

### 10.3 Визуальное различие
Для группы должен использоваться красивый и заметный значок. На уровне реализации это может быть:

- unicode-значок папки
- отдельная иконка
- префикс в названии

Предпочтителен вариант, который устойчиво работает в текущем `FreeSimpleGUI` и не ломает выравнивание таблицы.

### 10.4 Макеты интерфейса

- имя уже занято на текущем уровне
- имя содержит недопустимые символы Windows
- имя начинается с `.`, `__` или `~`
- новая группа превысит глубину вложенности 4

## 11. Совместимость с существующими сценариями

### 11.1 Создание проекта
Новый проект создается в текущей группе, если пользователь находится внутри группы. Иначе проект создается в корне `projects/`.

### 11.2 Редактирование проекта
Редактирование использует абсолютный путь выбранного проекта, а не предполагает, что проект лежит на верхнем уровне.

### 11.3 Копирование проекта
Копирование работает внутри текущего каталога проекта или в логике, уже принятой приложением, но с учетом вложенных путей.

### 11.4 Удаление
- удаление проекта продолжает удалять папку проекта
- удаление группы должно требовать подтверждения
- удаление непустой группы должно явно предупреждать о вложенных проектах и группах

## 12. Тестовая стратегия

### 12.1 Unit-уровень
- определение типа папки
- проверка, что пустая папка не отображается как группа
- сканирование вложенных групп
- проверка, что папка с `.env`, но без `ScriptName`, не отображается как проект
- сортировка групп выше проектов
- валидация имени группы
- валидация глубины
- валидация перемещения
- разворачивание группы в плоский список проектов

### 12.2 Интеграционный уровень
- сценарий с `projects/Demo/`
- создание группы из GUI
- переход внутрь и обратно через `..`
- запуск выделенной группы
- перемещение проекта в группу и в корень
- фильтрация служебной папки `projects/Демо_edt_в_cf/~0,-1`

## 13. Риски реализации

### 13.1 Риск: текущая таблица рассчитана на плоский список
**Решение:** ввести явную модель элементов и отображать только текущий уровень, а не все дерево сразу.

### 13.2 Риск: текущие операции add/edit/delete используют имя как уникальный идентификатор
**Решение:** перейти к использованию абсолютного пути элемента как основного идентификатора.

### 13.3 Риск: иконки или unicode могут выглядеть нестабильно
**Решение:** выбрать красивый, но безопасный символ или иконку, проверенную в текущем GUI-окружении.

### 13.4 Риск: частичные сбои при перемещении
**Решение:** перед файловой операцией валидировать все ограничения, а после любой ошибки выполнять повторное сканирование с диска.
