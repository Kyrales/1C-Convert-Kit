# Спецификация: Рефакторинг конвертеров с CMD на Python

## 1. Обзор

### 1.1 Цель
Переход от legacy CMD скриптов к современной Python-архитектуре конвертеров 1С с устранением дублирования кода и автоматическим обнаружением доступных конвертеров.

### 1.2 Контекст
Текущая система использует CMD скрипты в папках `src/converters/*/legacy/` для конвертации различных типов 1С объектов (конфигурации, обработки, расширения). Эти скрипты содержат много дублирующегося кода и требуют ручного управления в `convert.py`.

### 1.3 Преимущества новой архитектуры
- Единая кодовая база без дублирования
- Автоматическое обнаружение конвертеров
- Упрощенное добавление новых типов конвертации
- Лучшая тестируемость и поддерживаемость
- Единообразная обработка ошибок и логирование

## 2. Требования

### 2.1 Функциональные требования

#### FR-1: Базовый класс конвертера
**Приоритет:** Высокий  
**Описание:** Создать абстрактный базовый класс `BaseConverter` с общей логикой для всех конвертеров.

**Критерии приемки:**
- 1.1. Класс содержит методы для работы с .env файлами
- 1.2. Класс содержит методы для управления временными файлами
- 1.3. Класс содержит методы для логирования (info, error, warning, success) на русском языке
- 1.4. Класс содержит методы валидации параметров
- 1.5. Класс содержит абстрактные методы, которые должны реализовать наследники
- 1.6. Класс поддерживает работу с различными типами источников (EDT, XML, InfoBase)
- 1.7. При ошибке временные файлы сохраняются и путь к ним выводится в консоль
- 1.8. При успешной конвертации временные файлы удаляются

#### FR-2: Абстракция инструментов конвертации
**Приоритет:** Высокий  
**Описание:** Создать абстракцию для работы с инструментами 1С (designer, ibcmd, ring, edtcli).

**Критерии приемки:**
- 2.1. Создан класс `V8ToolWrapper` для работы с 1cv8.exe (designer)
- 2.2. Создан класс `IbcmdToolWrapper` для работы с ibcmd.exe
- 2.3. Создан класс `EdtToolWrapper` для работы с 1cedtcli/ring
- 2.4. Все классы наследуются от базового `ToolWrapper`
- 2.5. Классы автоматически находят инструменты в системе
- 2.6. Классы предоставляют единообразный интерфейс для выполнения команд

#### FR-3: Специализированные конвертеры
**Приоритет:** Высокий  
**Описание:** Создать специализированные конвертеры для каждого типа объектов 1С.

**Критерии приемки:**
- 3.1. Создан `ConfigurationConverter` для конвертации конфигураций (conf2cf, conf2xml, conf2edt)
- 3.2. Создан `DataProcessorConverter` для конвертации обработок/отчетов (dp2epf, dp2erf, dp2xml, dp2edt)
- 3.3. Создан `ExtensionConverter` для конвертации расширений (ext2cfe, ext2xml, ext2edt)
- 3.4. Создан `ValidationConverter` для валидации EDT проектов (edt-validate)
- 3.5. Каждый конвертер наследуется от `BaseConverter`
- 3.6. Каждый конвертер реализует специфичную логику конвертации

#### FR-4: Реестр конвертеров
**Приоритет:** Высокий  
**Описание:** Создать систему автоматического обнаружения и регистрации конвертеров.

**Критерии приемки:**
- 4.1. Создан файл `src/converters/registry.py` с классом `ConverterRegistry`
- 4.2. Реестр автоматически находит все Python конвертеры в папке `converters/`
- 4.3. Реестр предоставляет метод для получения конвертера по типу конвертации (conf2cf, dp2epf, ext2cfe и т.д.)
- 4.4. Реестр поддерживает регистрацию конвертеров через метод register()
- 4.5. Реестр валидирует корректность конвертеров при регистрации

**Примечание:** В .env файлах параметр ScriptName указывает тип конвертации:
- `ScriptName=conf2cf`
- `ScriptName=dp2epf`
- `ScriptName=ext2cfe`

#### FR-5: Интеграция с convert.py
**Приоритет:** Высокий  
**Описание:** Обновить `convert.py` для работы с новыми Python конвертерами.

**Критерии приемки:**
- 5.1. `convert.py` использует `ConverterRegistry` для получения конвертеров
- 5.2. Удалена функция `find_legacy_script()`
- 5.3. Удален код запуска CMD скриптов через subprocess
- 5.4. Сохранен интерфейс командной строки (аргументы --env, --output)
- 5.5. Сохранены функции работы с .env файлами (load_env_file, merge_env_files)

#### FR-6: Валидация параметров
**Приоритет:** Средний  
**Описание:** Реализовать валидацию параметров на уровне базового класса.

**Критерии приемки:**
- 6.1. Базовый класс валидирует обязательные параметры (V8_SRC_PATH, V8_DST_PATH)
- 6.2. Базовый класс валидирует существование путей источников
- 6.3. Базовый класс валидирует корректность путей назначения
- 6.4. Специализированные конвертеры могут добавлять свои правила валидации
- 6.5. Валидация выполняется до начала конвертации
- 6.6. Ошибки валидации содержат понятные сообщения

### 2.2 Нефункциональные требования

#### NFR-1: Производительность
- Время конвертации не должно увеличиться более чем на 5% по сравнению с legacy скриптами
- Последовательная обработка файлов (без параллелизма)

#### NFR-2: Совместимость
- Поддержка Windows и Linux
- Поддержка Python 3.8+
- Работа с .env файлами (требуется обновление ScriptName без .cmd)

#### NFR-3: Тестируемость
- Покрытие тестами не менее 80% нового кода
- Все существующие интеграционные тесты должны проходить
- Unit-тесты для каждого конвертера

#### NFR-4: Поддерживаемость
- Документация для каждого класса и метода
- Примеры использования в docstrings
- Логирование всех важных операций на русском языке

#### NFR-5: Обработка ошибок
- При ошибке конвертации работа прерывается
- Ошибки инструментов 1С парсятся и выводятся в понятном виде
- При ошибке временные файлы сохраняются для отладки
- Путь к временным файлам указывается в сообщении об ошибке

#### NFR-6: Логирование
- Цветной вывод в консоль (как в текущей версии)
- Все сообщения на русском языке
- Единый стиль сообщений (INFO, ERROR, WARNING, SUCCESS)
- Логи в файл не требуются

#### NFR-7: Прогресс выполнения
- В консоли: вывод текущего этапа конвертации
- В GUI: индикатор прогресса по этапам обработанных проектов (как в текущей версии)
- Информация о текущем обрабатываемом проекте

## 3. Архитектура

### 3.1 Структура модулей

```
src/converters/

├── registry.py                    # Реестр конвертеров
├── base/
│   ├── __init__.py
│   ├── converter.py              # BaseConverter
│   └── tools.py                  # Абстракции инструментов
├── configuration/
│   ├── __init__.py
│   ├── converter.py              # ConfigurationConverter
│   └── legacy/                   # Сохраняем для истории
├── dataprocessor/
│   ├── __init__.py

### 3.2 Диаграмма классов

```
┌─────────────────────┐
│   BaseConverter     │ (Abstract)
├─────────────────────┤
│ + env_vars: dict    │

│ + logger: Logger    │
├─────────────────────┤
│ + validate()        │
│ + convert()         │ (Abstract)
│ + cleanup()         │
│ + detect_source()   │ (Abstract)
└─────────────────────┘
         △
         │
    ┌────┴────┬────────────┬──────────────┐
    │         │            │              │
┌───┴───┐ ┌──┴──┐  ┌──────┴─────┐ ┌─────┴────┐
│Config │ │DP   │  │ Extension  │ │Validation│
│Conv.  │ │Conv.│  │ Converter  │ │Converter │
└───────┘ └─────┘  └────────────┘ └──────────┘
```

### 3.3 Поток выполнения

```
1. convert.py получает параметры командной строки
2. Загружает и объединяет .env файлы
3. Определяет ScriptName из .env
4. Запрашивает конвертер из ConverterRegistry
5. Создает экземпляр конвертера с параметрами
6. Вызывает converter.validate()
7. Вызывает converter.convert()
8. Вызывает converter.cleanup()
9. Возвращает результат
```

## 4. Специфичные параметры конвертеров

### 4.1 ConfigurationConverter
**Обязательные:**
- V8_SRC_PATH - путь к источнику (EDT/XML/InfoBase)
- V8_DST_PATH - путь к файлу .cf или папке EDT

**Опциональные:**
- V8_CONVERT_TOOL - инструмент (designer/ibcmd)
- V8_CONF_CLEAN_DST - очистка назначения

### 4.2 DataProcessorConverter
**Обязательные:**
- V8_SRC_PATH - путь к обработкам/отчетам
- V8_DST_PATH - путь к папке для .epf/.erf

**Опциональные:**
- V8_BASE_IB - базовая информационная база
- V8_BASE_CONFIG - базовая конфигурация
- V8_DP_CLEAN_DST - очистка назначения

### 4.3 ExtensionConverter
**Обязательные:**
- V8_SRC_PATH - путь к расширению
- V8_DST_PATH - путь к файлу .cfe
- V8_EXT_NAME - имя расширения

**Опциональные:**
- V8_BASE_IB - базовая информационная база
- V8_BASE_CONFIG - базовая конфигурация

### 4.4 ValidationConverter
**Обязательные:**
- V8_SRC_PATH - путь к EDT проекту

**Опциональные:**
- V8_EDT_VERSION - версия EDT

## 5. Миграция

### 5.1 Этапы миграции

**Этап 1: Создание базовой инфраструктуры**
- Создать BaseConverter
- Создать абстракции инструментов
- Создать ConverterRegistry

**Этап 2: Реализация конвертеров**
- Реализовать ConfigurationConverter
- Реализовать DataProcessorConverter
- Реализовать ExtensionConverter
- Реализовать ValidationConverter

**Этап 3: Интеграция**
- Обновить convert.py
- Обновить тесты
- Обновить документацию

**Этап 4: Удаление legacy кода**
- Удалить вызовы CMD скриптов из convert.py
- Переместить CMD скрипты в legacy/ (для истории)
- Обновить README

### 5.2 Обратная совместимость
Обратная совместимость с CMD скриптами **НЕ требуется**. Legacy скрипты сохраняются только для истории.

### 5.3 Миграция .env файлов
**Все существующие .env файлы необходимо обновить:**
- `ScriptName=conf2cf.cmd` → `ScriptName=conf2cf`
- `ScriptName=dp2epf.cmd` → `ScriptName=dp2epf`
- `ScriptName=ext2cfe.cmd` → `ScriptName=ext2cfe`

Это обязательное изменение для работы с новой архитектурой.

```

## 8. Риски и ограничения

### 8.1 Риски
- **Риск:** Изменение поведения при переходе с CMD на Python
  - **Митигация:** Тщательное тестирование с реальными проектами

- **Риск:** Проблемы с кодировками на Windows
  - **Митигация:** Использовать явное указание кодировок (cp1251, utf-8)

- **Риск:** Различия в работе subprocess между CMD и Python
  - **Митигация:** Тестирование на разных версиях Windows

### 8.2 Ограничения
- Поддержка Windows и Linux
- Требуется установленная платформа 1С
- Требуется Python 3.8+

## 9. Критерии успеха

1. Все существующие интеграционные тесты проходят
2. Новые unit-тесты покрывают не менее 80% кода
3. Время конвертации не увеличилось более чем на 5%
4. Код не содержит дублирования логики между конвертерами
5. Добавление нового типа конвертера требует только создания одного класса
6. Документация полная и актуальная
